# IMStage Eval：标注、金标与回归

本阶段由用户明确授权搭建 Eval。标注工具独立于尚在开发的 Web、MCP/API 和生产渲染器，不据此批准其他产品架构、云部署或付费服务。

## 先建立什么

让维护者实际完成：录入问题与素材 → 定义预期 → 导入候选 PNG → 判断好坏及原因 → 明确确认金标 → 导出版本化数据 → 用新的候选结果运行回归。普通截图和长截图都是 PNG，但尺寸和完整性要求独立保存。

运行和数据格式见 [Eval 工具说明](../tools/eval/README.md)。本地启动入口是 `npm --prefix tools/eval start`，默认仅监听 `http://127.0.0.1:4421`。个人标注与上传素材保存在忽略目录 `.local/eval/`，不会随源码提交。

## 用例的五个维度

| 维度 | 初始选项 | 判断目的 |
| --- | --- | --- |
| 目标环境 | iOS、Android、Desktop、Web | 同一 IM 在不同环境的视觉规格不混比 |
| IM | 微信、Telegram、WhatsApp、自定义 | 允许逐步扩展，不代表已经实现各平台渲染器 |
| 输入 | question、语言、图片、视频、音频、其他附件 | 原始素材与解析结果分离；本期保存素材，不声称已解析 |
| 场景 | 预期说明，可写单聊、群聊、系统提示等 | 建立可复现的任务和验收要求 |
| 输出 | 普通 PNG / 长 PNG、宽高 | 固定输出契约；不以“返回了文件”代替正确性 |

先标少量有代表性的案例：每个重点 IM 至少包含普通图、长图、混合语言、带媒体消息、明显错误和边界内容。无需穷举所有组合；覆盖统计应暴露缺口，而不是用总平均分掩盖某平台的退化。

## 人工判断

四个维度分别采用 0 / 1 / 2 分：

| 维度 | 0：不通过 | 1：需要改进 | 2：满足预期 |
| --- | --- | --- | --- |
| 内容正确 | 人物、内容或顺序错误 | 有局部偏差 | 符合问题与明确预期 |
| IM 风格 | 目标平台错误或明显不符 | 有样式偏差 | 符合所选 IM 与环境 |
| 布局 | 遮挡、溢出或不可读 | 可用但有瑕疵 | 清晰、对齐、无裁切问题 |
| 完整性 | 缺失关键消息/媒体/尾部 | 次要元素缺失 | 预期内容完整呈现 |

最终好坏由标注者明确选择并解释原因；数字评分帮助分析，不自行替代最终判断。坏例留作错误样本，不会作为好的视觉基准。合成示例初始为待审核，不能冒充用户金标。

审核绑定当前用例指纹；修改问题、素材、目标、预期或候选输出会撤销之前的审核和金标。输入发生变化时，需要重新导入对应输出。多窗口保存使用 revision 检测冲突，不能静默覆盖。

## 自动评测的实际含义

| 检查 | 本期行为 | 不能证明的事 |
| --- | --- | --- |
| 数据与溯源 | 版本、用例 ID、输入指纹、PNG 哈希、完整性 | 素材授权是否真实 |
| 格式和尺寸 | 验证真实 PNG，限制像素数，严格比较宽高 | 图片内容正确 |
| 视觉回归 | 比较当前候选与人工确认图片的像素差异率，输出差异图 | 语义等价、审美或真实 IM 一致性 |
| 覆盖率 | 按 IM、环境、语言、素材类型和截图种类汇总 | 未覆盖组合正确 |
| 人工语义与视觉评价 | 保存四项评分、最终判断和原因 | 自动 OCR、多模态理解或 LLM judge 已实现 |

默认像素差异率上限是 **0.5%**，像素颜色判断阈值是 **0.1**；这只是起始配置，不是从用户金标校准出的质量标准。先用好坏例观察误报/漏报，再按用例调整。缺图、无金标、错误尺寸、陈旧输入和非法数据必须失败，不能计作零差异或跳过后全绿。

视觉基准应在固定渲染环境里生成：浏览器、字体、viewport、DPR、时区和时间内容保持一致。运行于不同 OS 的工具自检不代表已经保证不同 OS 的文字栅格化完全一致。

## Git 与 CI 的连接

1. 人工标注在本地进行，保留原始输入、预期和候选的分离。
2. 只有明确标为合成且人工确认的金标才通过 Git/CI 导出入口；公开前仍需检查文件。真实聊天、个人截图和私有素材不进入此仓库。
3. 将导出的金标作为版本化文件纳入 PR；阈值和基准更新也要在 diff 中审查，禁止 CI 自动接受新图片。
4. 产品渲染器或 CI 上游步骤针对该金标版本生成新的 actual manifest，再调用 `node tools/eval/cli.mjs evaluate --gold GOLD.json --actual ACTUAL.json --out REPORT_DIR`。
5. CI 保存 JSON / Markdown / 差异图；失败阻止相应质量检查。缺少结果时不能从金标复制 actual 来制造通过。

本次 GitHub workflow 名为 **Eval harness**，检查标注工具与评测器的正反例。它证明评测基础设施能够发现预置退化，**不是 IMStage 产品质量门禁**。生产渲染器、稳定字体环境和经过用户审核的真实金标集接入后，才能启用产品回归 required check。

仓库同时提供 [可复用 GitHub Action](../.github/actions/imstage-eval/action.yml)。在同一个 job 内，先 checkout 仓库、由真实渲染步骤生成 actual 文件，再调用：

```yaml
- uses: ./.github/actions/imstage-eval
  with:
    gold: path/to/reviewed-gold.json
    actual: path/to/new-actual.json
    artifact-name: renderer-eval-report
```

这些路径是接入示例，不是已存在的产品数据集。Action 会执行比较并在失败时保留报告；它不会生成候选图，也不会更新金标。多个 matrix job 调用时要使用不同的 artifact-name。

## 后续决策

- 用户逐步确认首批 IM、环境、导出规格与评分标准。
- 在共享 conversation contract 稳定后，添加人物、消息顺序、消息类型和素材引用的结构化断言；不要只依赖图像 diff。
- 自然语言与多模态解析属于非确定性阶段，应单独记录模型/提示词版本、重复运行结果与成本；渲染回归保持确定性。
- 是否增加 OCR、区域标注、多人复核、远程存储、保留期与自动模型评判，按真实标注反馈决定。

## 实现依据

- [Node.js 22 文件 API](https://nodejs.org/docs/latest-v22.x/api/fs.html#fspromisesrenameoldpath-newpath)：本地文件持久化；应用层另行处理冲突与校验。
- [pngjs](https://github.com/pngjs/pngjs)：PNG 编解码。
- [pixelmatch](https://github.com/mapbox/pixelmatch)：像素差异及可视化，不将其解释为语义质量分数。
- [GitHub upload-artifact](https://github.com/actions/upload-artifact)：上传明确指定的评测报告目录，排除本地个人数据目录。
